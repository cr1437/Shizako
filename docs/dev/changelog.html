zako4 更新日志#

这一版的主线是「让日常用起来更顺」：把启动路径、列表渲染和后台唤醒重新收拾了一遍（性能与耗电是本次重点），同时补上一批早就想要的能力 —— 应用数据备份/恢复（含特权存储代理）、安装信任列表与批量队列、EXEC_SHELL 自动化。

⚡ 性能与耗电（本版重点）#

  • Baseline Profile 真正进包：构建脚本此前把 CompileArtProfileTask 全局禁用，421 KB 的 baseline-prof.txt 每次都会生成却从未打进 APK —— Compose / Material3 / RecyclerView 自带的基线配置一起被丢掉，冷启动只能靠 JIT 解释执行。现在移除禁用，release 包内可见 assets/dexopt/baseline.prof，冷启动重新吃到 AOT 预编译
  • 应用列表图标真正命中缓存：列表项绑定时先查 AppIconCache（按 uid + 目标尺寸缓存），命中直接上屏，不再每次新建 item 都在主线程同步 loadIcon；未命中才异步替换，滚动更稳
  • 列表不再随内容反复测量：RecyclerView.setHasFixedSize(true) + 固定条目标高，过滤/刷新时少一轮 requestLayout
  • 后台唤醒收敛（省电也是体验的一部分）：
  • 更新检查：AlarmManager.RTC_WAKEUP → JobScheduler（6 小时周期、持久化、按网络条件触发），不再周期性把设备从待机叫醒
  • 无障碍守护心跳自适应：前台 60s / 息屏 5min / 省电 10min
  • 保活 shell 轮询 sleep 45 → sleep 90，减少无意义唤醒与闪存写入
  • 首页状态只探活一次：单次 binder 探活失败不再把整页判成「服务未运行」，onResume 再校准，减少无效重载与状态闪烁

✨ 新功能#

  • 应用数据备份 / 恢复（应用管理 → 右上角「应用数据备份与恢复」）
  • 外部数据（/sdcard/Android/data、/sdcard/Android/obb）打包成 external.tar.gz，可选一并保存 OBB / APK；边读边写用户选的 SAF 目录，设备上不落临时包
  • 恢复是替换式：先解到 staging，成功后按顶层条目替换，解压失败原数据一个字节不动；恢复前二次确认，OBB 失败单独报告，未安装会提示先安装（备份里带 APK 时可直接交给安装器）
  • 批量备份队列：顺序执行、单项失败不中断、可取消
  • 特权存储代理 IStorageProxy：shell/root 服务进程提供的受限文件接口（列目录 / 开文件 / tar 打包 / 安全解压 / 复制 / 删除 / 建目录 / 存在性），四层访问降级（直连 → shell 管道 → run-as（仅 debuggable）→ content://），所有路径先过白名单与注入校验；第三方应用需在「第三方调用」页单独授权，每次调用写审计
  • 安装信任列表 + 批量安装队列：apk / apk.1 / XAPK / APKS，签名与 uid 双校验的受信直装、外部应用请求的确认框、队列顺序执行与历史记录
  • EXEC_SHELL 自动化：带令牌与签名校验的广播入口，结果按调用方包名回传
  • 批量授权 / 权限模板：多选批量授予/撤销、影响确认、3 个内置模板 + 自定义模板、SAF 导出/导入
  • 应用管理页新增存储代理与数据备份入口；设置页补齐安装 / 自动化分区

🔧 修复#

  • 授权弹窗点了「确定」不生效（CountDownLatch.await 返回值误判 + 冷启动没有 binder + 只按本 fork 的权限名 grant）
  • 首页偶发显示「服务未运行」（单点探活失败被判成整体失败）
  • API 24 应用管理列表为空（getInstalledPackages 只找 (long,int) 签名，缺 (int,int) 回退）
  • 服务端一处空指针：同一进程二次连接后应用永久收不到 binder
  • 共享 uid 下只有第一个包能收到 binder
  • Android 7.x 上模块 / WebUI 因 java.nio.file（API 26）崩溃等 17 处首次引导与低版本兼容问题
  • 模块 / WebUI 的非 root 工作目录回退与若干文案

🌍 English#

This release is mainly about making daily use smoother: the startup path, list rendering and background wake-ups were reworked (performance and battery are the focus), together with app data backup/restore (with a privileged storage proxy), a trusted-installer list with a batch queue, and EXEC_SHELL automation.

  • Performance: Baseline Profile is now actually packaged (the build used to disable CompileArtProfileTask, so the generated baseline-prof.txt never reached the APK); app-list icons now hit a real cache; fixed-size list items; update checks moved from AlarmManager to JobScheduler, adaptive accessibility heartbeat, keep-alive polling 45s → 90s; single-probe home status.
  • New: external-data backup/restore (tar.gz streamed straight into a SAF folder, replace-style restore that leaves your data untouched if extraction fails, batch queue); IStorageProxy with four-layer fallback plus a whitelist and injection guard; trusted installers and a batch install queue (apk / apk.1 / XAPK / APKS); EXEC_SHELL automation; batch permission grants and templates.
  • Fixed: the permission dialog's "allow" not taking effect, home status flicker, an empty app list on API 24, a server NPE after re-connect, shared-UID binder push stopping after the first package, and the background wake-up issues listed above.

zako3.19hp 更新日志#

热修复版：把 Dhizuku（设备所有者）这条线补完整 —— 激活/委派用的组件名从 3.10 起就是错的（#13），「一键激活」因此从未成功；成为设备所有者之后也没有任何退出入口，adb 也移不掉（#12）。这一版两个都修了，并回应了 Play Protect 误报的说明（#11）。

🔧 修复#

  • Dhizuku 激活命令组件名错误（#13）：应用内拼的是 com.churan.shizako.dhizuku.DhizukuAdminReceiver，但 manifest 里 .dhizuku.DhizukuAdminReceiver 实际相对 namespace（moe.shizuku.manager）解析，真实组件是 com.churan.shizako/moe.shizuku.manager.dhizuku.DhizukuAdminReceiver。所以「查看命令」给出的 adb 命令必然 Unknown admin，一键激活也从未成功。现在组件名由真实类名生成，命令/激活/委派统一走它
  • 已授权应用拿不到设备所有者权限（#13 关联）：同一个错误组件也被 setDelegatedScopes / getDelegatedScopes 使用，调用必抛 SecurityException。这正是「能授权、但应用用不了设备所有者权限」的原因，已随组件修复一并解决
  • 无法取消设备所有者（#12）：激活页的 Dhizuku 卡片和应用页的「Dhizuku 应用」页都新增了「取消设备所有者」按钮（带确认弹窗）。设备所有者可以清掉自己（DevicePolicyManager.clearDeviceOwnerApp），不需要 adb、不需要服务在跑；adb shell dpm remove-active-admin 对正式包（非 testOnly admin）本来就无效。入口按「真实设备所有者状态」判断，所以先把「Dhizuku 模式」开关关掉也不会丢掉退出入口

📝 说明#

  • Play Protect 误报（#11）：Play Protect 把 Shizako 标成 harmful 是 Google 侧对「侧载 + Shizuku 类特权应用」的启发式判定，不是应用含恶意代码，也无法在代码里关闭。README 新增了 FAQ：如何用 apksigner verify --print-certs 核对证书 SHA-256（515baf0c…9f9c8a）、确认无误后如何保留安装、以及向 Google 提交误报申诉的入口。内部也在收窄会让模型误判的能力面（去掉不再使用的声明、收紧自动化入口），但不承诺以后一定不再被标记

Both are fixed here, plus a note on the Play Protect false positive (#11).

  • Wrong Dhizuku activation component (#13): the app built com.churan.shizako.dhizuku.DhizukuAdminReceiver, but .dhizuku.DhizukuAdminReceiver in the manifest resolves against the namespace (moe.shizuku.manager), so the real component is com.churan.shizako/moe.shizuku.manager.dhizuku.DhizukuAdminReceiver. zako3.19 更新日志#

这一版真正修好了「无线调试配对/激活」：定位到两个根因 —— 配对连接被连到 0 号端口、服务进程被 ADB shell 的挂断信号在 exec 前杀掉；同时移除了只用于排查的首页「诊断日志」测试功能，它不会再出现在源码与发布包里。

🔧 修复#

  • 无线调试配对永远「连不上」：AdbPairingClient 为加连接超时改用了 Socket().apply { connect(InetSocketAddress(host, port), …) }，而 apply 的接收者是 Socket，Socket 自带 getPort()（未连接时恒为 0），于是 port 被解析成 0 —— 每次配对都在连 127.0.0.1:0，必然 ECONNREFUSED。现在先用局部变量固定端口再连接，tcp connect -> host:port 日志也会打印真实端口
  • 配对成功但服务起不来（Untracked pid … received signal 1）：通过 ADB shell 启动服务时，adbd 会在 shell 通道关闭的一刻给前台进程组发 SIGHUP；服务子进程在 fork() 到 setsid() 之间有一个极小的窗口，信号落进去就会把还没 exec 的进程杀掉。现在 starter 在 fork 之前就忽略 SIGHUP/SIGPIPE（SIG_IGN 会被子进程继承且 exec 后仍有效），Root 路径不受影响
  • 旧服务进程清理从未生效：app_process --nice-name= 会把 /proc/<pid>/cmdline 改写只剩昵称，原来「cmdline 含包名 + 类名」的匹配永远命中不了，升级后会出现两个 shizako_server 抢注册同一个 binder。现在按昵称 + /proc/<pid>/maps 精确识别，既清得掉自己的旧进程，也不会误杀官方 Shizuku
  • 启动顺序：先在当前可用的无线调试端口上把服务拉起来，再尽力切到固定 TCP 5555；切换失败只记日志，不再让「可选优化」挡住激活
  • 配对端口更稳：连接被拒时自动换 mDNS 最新端口重试；分屏配对也覆盖 ConnectException；_adb-tls-connect._tcp 发现窗口 3s → 6s；局域网兜底地址改为所有非回环 IPv4（Wi-Fi 优先）
  • 失败可见：配对成功但服务没起来会给出可见通知，不再只写日志

🗑️ 移除#

  • 首页「诊断日志」测试功能（仅 -PlogBuild 排查包含有）：删除 diag/DiagLog.kt、home/DiagLogViewHolder.kt、layout/home_diag_log.xml，去掉 -PlogBuild 开关、LOG_BUILD 编译期字段、-log 版本后缀与全部相关文案。正式版与排查包都不会再包含它，源码上传到 GitHub 时也不带这段测试代码

🌍 English#

This release actually fixes wireless-debugging pairing/activation: two root causes were found — pair connections dialled port 0, and the server process was killed by the ADB shell hang-up before exec; the home-page "Diagnostics log" test feature (log builds only) was removed from source and releases.

  • Pairing could never connect: Socket().apply { connect(InetSocketAddress(host, port), …) } resolves port to Socket.getPort() (0 when unconnected), so every attempt dialled 127.0.0.1:0. The port is now captured in a local variable before connecting, and logs print the real port
  • Pairing succeeded but the service never started: adbd sends SIGHUP to the shell's process group when the channel closes, and the server child could be killed between fork() and setsid() (Untracked pid … received signal 1). The starter now ignores SIGHUP/SIGPIPE before forking (SIG_IGN survives exec); the root path is unaffected
  • Stale server cleanup never worked: app_process --nice-name= rewrites /proc/<pid>/cmdline to the nickname, so the old "package + server class" match never fired and two shizako_server processes could fight over the binder. Identification now uses the nickname plus /proc/<pid>/maps, so our own old servers are cleaned up while the official Shizuku is left alone
  • Start order: bring the service up on the currently working wireless port first, then best-effort switch to TCP 5555; a failed switch no longer blocks activation
  • Pairing is more resilient: retry with the freshest mDNS port after a refused connect, handle ConnectException in the split-screen dialog, extend _adb-tls-connect._tcp discovery from 3s to 6s, and fall back to all non-loopback IPv4 addresses (Wi-Fi first)
  • Failures are visible: a notification is posted when pairing succeeds but the service does not start

🗑️ Removed#

  • The home-page "Diagnostics log" test feature (log builds only) is gone: diag/DiagLog.kt, home/DiagLogViewHolder.kt, layout/home_diag_log.xml, the -PlogBuild switch, LOG_BUILD build field, -log version suffix and all related strings were deleted. It no longer ships in any build and is not part of the source pushed to GitHub.

zako3.17 更新日志#

修掉一个会打到所有「同时装了官方 Shizuku」的用户的启动问题，以及通知栏配对时端口可能丢失的隐患。versionCode 抬到 317 —— 这是为了进 F-Droid（它只比 versionCode），也顺带把版本名按惯例对回 3.17。

🔧 修复与优化#

  • 与官方 Shizuku 并存时启动失败、甚至互杀：本应用的服务进程原本也叫 shizuku_server，而 starter 在启动前会按进程名杀掉所有同名进程。官方 Shizuku 的服务进程正好同名，于是两种坏法都会出现 —— 对方以 root 运行时杀不动，starter 直接 fatal: can't kill … 退出；两边身份相同时，则会把对方的 server 悄悄杀掉。现在服务进程改名为 shizako_server，清理逻辑也改为只杀「cmdline 里同时包含本应用包名与服务类名」的进程，从旧版本升级上来的旧名字进程同样能被认出。README 承诺的「可与官方 Shizuku 共存」从这一版起才真正成立
  • 通知栏配对可能带着错误的端口去连接：端口和配对码以前共用同一个 extra key（paring_code），PendingIntent 又是先按 -1 建好、再靠 FLAG_UPDATE_CURRENT 就地改 extra。现在端口改用独立 key（pairing_port），每个端口各建一个 PendingIntent；收到的端口先校验 1..65535，不合法就不发起连接并直接说明原因，不会再出现「明明发现了 46499，却去连 0 号端口」
  • 连接前先确认配对服务还活着：系统「使用配对码配对设备」对话框一关，adbd 就把配对端口收回去，那之后再连只会得到 ECONNREFUSED。通知栏与分屏对话框两条路径现在都会在连接前探测端口，命中就明确提示「配对服务已停止监听（端口 N）」，并告诉你重开对话框，而不是笼统地报一句「连不上」
  • 配对流程补了现场日志：pairing reply received: port=…（端口有没有传到、传成了几）、pairing start: hosts=[…] port=…、resolved type=_adb-tls-pairing._tcp … listening=…，再遇到「配对连不上」时一眼就能定位是发现、端口传递还是连接环节的问题

🌍 English#

Fixes a start-up problem that hits everyone who also has the official Shizuku installed, plus a port hand-off flaw in notification-based pairing. versionCode is now 317 — required by F-Droid, which only compares version codes; the version name goes back to the numeric convention as 3.17.

  • Start-up failed — and could kill the other manager — when the official Shizuku was installed: our server process was also called shizuku_server, and the starter kills every process with that name before starting. With the upstream server running as root the kill fails and the starter exits with fatal: can't kill …; with both running under the same identity it silently killed Shizuku's server instead. The process is now shizako_server, and the starter only kills processes whose cmdline contains both our application id and our server class — which also recognises an old-name server left over from an upgrade
  • Notification-based pairing could connect with the wrong port: the port shared one extra key with the pairing code (paring_code), and the PendingIntent was created once with -1 and then "updated" via FLAG_UPDATE_CURRENT. The port now has its own key (pairing_port), each port gets its own PendingIntent, and a port outside 1..65535 aborts before any socket is opened instead of dialling port 0
  • The pairing port is probed before connecting: once the system "Pair device with pairing code" dialog closes, adbd releases that port and any later connect can only return ECONNREFUSED. Both the notification and the split-screen dialog now probe it first and say "the pairing service has stopped listening (port N) — reopen that dialog" instead of a bare "can't connect"
  • Better logs for pairing: pairing reply received: port=…, pairing start: hosts=[…] port=…, resolved type=_adb-tls-pairing._tcp … listening=…

zako3.16hp 更新日志#

修复 zako3.16 留下的问题：Root 激活广播必崩、配对在个别设备上连不上、配对每次尝试都会泄漏一个 socket 与一块原生密钥内存，以及低频恢复会永远空转而通知还在宣称「正在重试」；另外新增「简单 / 进阶」双模式，把大部分人用不到的功能收起来。 versionCode 仍为 316，只是 versionName 加 hp 后缀，可直接覆盖安装 zako3.16。

✨ 新增#

  • 简单 / 进阶双模式：有人反馈功能太多、一眼不知道该点哪儿。现在分两档，开关在首页服务器状态卡下面那张卡片上（整张卡可点）。简单模式下收起：底栏的日志 / 模块 / 控制台，工具箱的模块整组 / 控制台整组 / 实验室，以及设置里的底部栏、稳定性与自动化、API 日志；无障碍、激活、应用管理这些常用入口保留。选择会被记住 —— 这次开了进阶，下次打开还在进阶
  • 档位不是散在界面里 if 判断的：每个入口自带 FeatureLevel，由一处统一裁决。以后加功能只要标一下档位，不会出现「简单模式下还能点到」的破漏

🔧 修复与优化#

  • 实时磨砂现在拨了开关立刻生效：以前它只在 Activity 创建时读一次，所以必须在设置里拨完、退出 App、再重进才看得到效果。现在开关状态是运行时可观察的，拨完当帧就把快照层接上/关掉并同步底栏可见性，不用重建 Activity。顺带收紧了代价：非玻璃风格下不再开着整屏快照录制（那层离屏 RenderNode 每帧都会把内容重录一遍）
  • Root 激活不再崩溃（真机必现）：用 Tasker / MacroDroid 发 START_ROOT（或 START 且上次是 Root 模式）时，App 必定崩溃 —— 回调跑在没有 Looper 的线程上却直接弹 Toast，抛出 Can't toast on a thread that has not called Looper.prepare()。更别扭的是崩溃发生在服务已经起来之后，所以现象是「服务起来了，App 却没了」。已改为切主线程弹提示。这条是公开的广播接口，已 root 的设备最容易踩到
  • 配对增加局域网地址兜底：此前只连 127.0.0.1；个别设备/ROM 上应用连不上自己的回环地址（有用户反馈：同一台设备上 Termux 与电脑都能配对，本应用却连接被拒）。现在先试回环，只有在连接立刻失败时才改用本机局域网 IPv4 重试；配对码错误、协议层失败仍然立刻报错，不会让你白等两轮
  • 配对不再泄漏资源：AdbPairingClient 实现了可关闭接口，但配对服务与配对对话框两处都从不关闭它——每次配对尝试（包括失败后的重试）都会泄漏两个文件描述符（原始 socket 与 TLS socket）以及一块原生内存，而那块内存里存着 SPAKE2 密钥的拷贝。现在配对流程自身负责清理，无论成功、失败还是中途异常都会回收
  • 建连阶段失败也会清理：此前若在建立 TLS 连接时就失败（端口不通、握手失败、读取超时），清理逻辑会被整段跳过；现在这类失败同样会销毁原生上下文
  • 重复销毁不再有风险：原生销毁入口补上空指针与重复调用两道防线，销毁后清空指针并抹掉密钥材料；「本端配对消息」为空的极端情况改抛具名错误，而不是崩溃
  • 低频恢复现在有出口：此前若上次是无线调试激活、但固定端口 5555 不通、又拿不到自动开启无线调试所需的权限，恢复逻辑会什么都不做却每 5 分钟唤醒一次，永远等不到成功，而常驻通知仍在显示「正在重试」。现在这种情况会停止重试，并把通知改为如实的「自动重连已放弃——请手动启动服务（或重新授权限 / 改用 Root）」；另外增加了约 1 小时的尝试上限，避免无限唤醒耗电
  • 更正 zako3.16 的措辞：下面 zako3.16 一节写的「每 5 分钟探测并拉起一次，直到成功」不再准确——现在低频恢复有明确出口。正常使用（能拉起的情况）行为不变
  • 配对日志可诊断：握手成功时会打印 Handshake succeeded via <host>:<port>，遇到「配对连不上」时看一眼日志就知道是否走了局域网兜底
  • 配对端口文案不再有歧义：无线调试页面顶部那个「IP 地址和端口」是连接端口，配对要用的是「使用配对码配对设备」对话框里显示的端口。此前输入框只写「端口号」、提示又说「按无线调试页面显示的配对端口填写」，很容易填成顶部那个；而填错的表现是握手阶段报证书校验失败（adbd 的连接服务会校验客户端证书，配对服务则不校验）。现在标签改为「配对端口」，提示与错误文案都明确指出两者的区别
  • 配对填错端口会当场拦下并自动纠正：配对时会同时探一遍连接端口；如果你填的正是它，会直接提示「这是连接端口，不是配对端口」，并在已知配对端口时自动换上去。另加一层恢复：若握手阶段失败、而 mDNS 另外探到了配对端口，会自动用那个端口重试一次 —— 这种情况多半就是填成了连接端口
  • 配对失败现在能看到原因：错误提示里附上「端口 · 异常类型」，截图就能说明问题；AdbPairClient 同时记录 pairing start、TLS handshake -> host:port、失败阶段与异常，不用再靠猜是「连不上」「握手失败」还是「协议层失败」
